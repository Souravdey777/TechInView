**Short answer:** a **software engineer resume ATS** pass needs a single-column layout, plain-text section headings, contact details in the body, and skills written as text rather than icons. Once it parses, a person skims it in well under a minute, so each bullet should say what you did, how, and what changed.

The goal of the resume is narrow: get you to the phone screen. After that, your interview performance does the work, which is where the [90-day plan](/blog/90-day-coding-interview-prep-plan) and [problem-reading habits](/blog/how-to-read-coding-interview-problems) come in.

TechInView does not edit resumes. It is for practising the interviews you get once the resume works.

## What breaks ATS parsing

| Mistake | Fix |
|---------|-----|
| Multi-column layouts and text boxes | One column, standard sections |
| Icons instead of section headings | Plain text: Experience, Education, Skills |
| Key details in headers or footers | Keep contact info in the body |
| Tables for main content | Do not use them for roles and dates |
| Skills shown as logos or graphics | Write them out as text |
| Unusual fonts | Common system fonts |

A quick test: copy all the text out of your PDF and paste it into a plain text editor. If the order comes out scrambled, a parser may struggle too.

## The human skim

A hiring manager reading your resume is usually checking:

1. **Fit:** language, domain and scale close to the role
2. **Impact:** numbers, scope, what you owned
3. **Trajectory:** promotions or growing scope over time
4. **Density:** short bullets, not a paragraph per job

A bullet formula that works: **action + what + how + result** (a number where you have one, a clear qualitative result where you do not).

For example: "Cut p95 checkout latency from 800ms to 220ms by caching catalog fragments in Redis and removing N+1 ORM queries."

## Keywords: honest, not stuffed

Use the target job description's wording where it truthfully describes you:

- Languages, frameworks, cloud platforms, data stores
- Scale (requests per second, users, data volume) when you can stand behind the number
- Reliability work (SLOs, incident response) for senior roles

Do not list skills you cannot talk about in depth. Interviewers pick questions from what you claim, and a [technical Q&A round](/blog/technical-qa-interview-round-prep) will find the gaps quickly. The [job description prep guide](/blog/job-description-interview-prep) shows how to read a posting for this.

## Default section order

1. **Header:** name, email, GitHub and LinkedIn, location or "open to remote"
2. **Summary:** two lines at most, role plus specialty plus one proof point
3. **Experience:** reverse chronological
4. **Projects:** if you are early career or changing direction, with links
5. **Education**
6. **Skills:** grouped, for example Languages, Infrastructure, Data

## FAQ

### One page or two?

New grads and engineers with under five years of experience: aim for one page. Senior engineers with several shipped systems can use two if every line is pulling its weight.

### Should I include a photo?

For US and UK tech roles, generally no. Conventions differ in other countries, so check local norms.

### PDF or DOCX?

PDF keeps your layout intact. Use DOCX only if the application portal asks for it.
